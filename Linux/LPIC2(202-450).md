## BIND DNS SERVER

### Why DNS is Needed

Without DNS:
- Every application must use IP addresses.
- IP changes would break everything.
- Impossible to remember thousands of IP addresses.

DNS provides:
- Name resolution
- Mail routing
- Service discovery
- Load balancing
- Redundancy
- Reverse lookups
- Security extensions (DNSSEC)

BIND or Berkeley Internet Name Domain is open-source software that implements DNS protocols for the internet.

Installing:
`sudo apt install bind9 bind9-utils dnsutils`

### Creating Forward Lookup Zones

Zone Definition:
```
zone "example.com" {
    type master;
    file "/etc/bind/db.example.com";
};
```

Zone File:
```
$TTL 86400

# Every zone begins with exactly one SOA record. It contains administrative information about the zone.
@ IN SOA ns1.example.com. admin.example.com. (
    2026071801 ; Serial
    3600       ; Refresh
    900        ; Retry
    604800     ; Expire
    86400      ; Minimum TTL
)

@       IN NS ns1.example.com.

ns1     IN A 192.168.10.2

www     IN A 192.168.10.10

mail    IN A 192.168.10.20
```

Common Record Types:
| Record | Purpose            |
| ------ | ------------------ |
| A      | IPv4               |
| AAAA   | IPv6               |
| CNAME  | Alias              |
| MX     | Mail server        |
| NS     | Name server        |
| TXT    | Text/SPF/DKIM      |
| SRV    | Service discovery  |
| SOA    | Start of Authority |
| PTR    | Reverse lookup     |

| Record    | Purpose                    | Example                              |
| --------- | -------------------------- | ------------------------------------ |
| **SOA**   | Zone metadata              | Primary DNS server and serial number |
| **NS**    | Authoritative name servers | `example.com → ns1.example.com`      |
| **A**     | Hostname → IPv4            | `www → 192.168.1.10`                 |
| **AAAA**  | Hostname → IPv6            | `www → 2001:db8::10`                 |
| **CNAME** | Alias → Canonical hostname | `ftp → www`                          |
| **MX**    | Mail server                | `example.com → mail.example.com`     |
| **PTR**   | IPv4/IPv6 → Hostname       | `192.168.1.10 → www.example.com`     |
| **TXT**   | Arbitrary text             | SPF, DKIM, DMARC, verification       |
| **SRV**   | Service location           | LDAP, SIP, Kerberos, AD              |

### Authoritative vs Recursive DNS Servers
Recursive DNS Servers like 8.8.8.8 search recursive and cache the answer.
An authoritative server is the official owner of a domain's DNS records. It does not search other DNS servers.

In BIND:

Authoritative server:
```
zone "example.com" {
    type master;
    file "/etc/bind/db.example.com";
};
```
Recursive resolver:
```
options {
    recursion yes;
};
```
Public authoritative servers usually disable recursion:
```
options {
    recursion no;
};
```

### Virtual Hosts
In Apache, a website is a virtual server and Allows one Apache node to host multiple sites that Called "Virtual Hosts" in the configuration.

**Uniquely identifying sites**
- DNS name
	- Typically subdomains
	- prod.lab.itpro.tv
	- dev.lab.itpro.tv
	- sales.lab.itpro.tv
- IP Address
	- One NIC can host many IPs
	- Apache can bond sites to IPs

### Redirect urls

* Redirect Types
	- 301 (permanent)
	- 302 (temporary)
* Enabling htaccess files
	+ `vim /etc/apache2/sites-available/<name>`
		- `AllowOverride All`
	+ `.htaccess` file is placed in the website content folder
* Basic redirects(in .htaccess)
	+ Redirect a file to another file
		- `Redirect 301 /old.html /new.html`
	+ Redirecting all URLs to another domain
		- `Redirect 301 / https://newsite.com/`
	+ Redirect a single directory to another site
		- `Redirect 301 /account/ https://newsite.com/account/`
* Using context matching and regex
	+ Redirect from a directory to another
		- `RedirectMatch 301 ^/shop/ /products/`	# Example:  /shop/shoes → /products/shoes
	+ Redirecting an old directory to new directory
		- `RewriteRule ^blog/(.*)/(.*)/(.*)$ /news/$2/$1/$3 [R=301,NC,L]` # Example: /blog/2024/12/25 → /news/12/2024/25
	+ Options
		- `R`  - Redirect. Indicates an external redirect
		- `NC` - No case. Disables case sensitivity
		- `L`  - Last. Do not apply any other rules, Stop processing rules if this one matches
* Real-world examples
	+ Adding www and redirecting to HTTPS:
		- `RewriteEngine On`
		- `RewriteCond %{HTTP_HOST} ^website.com`
		- `RewriteRule (.*) https://www.website.com/$1 [R=301,L]` 
		
	+ Check if it's website.com OR site.com then redirect to https://www.website.com/
		- `RewriteEngine On`
		- `RewriteCond %{HTTP_HOST} ^website\.com [OR]`
		- `RewriteCond %{HTTP_HOST} ^site\.com`
		- `RewriteRule (.*) https://www.website.com/$1 [R=301,L]`

### Reverse Proxy
Why Use a Reverse Proxy?
- No Internal ports exposed
- HTTPS termination(reduce load on apps)
- Easy scaling
- central logging
- rate limiting
- caching
- One public IPs needs for all services

Examples:
```
server {
    listen 80;
    server_name example.com;

    location / {

        proxy_pass http://192.168.10.20:3000;
		
		proxy_set_header Host $host;
	    proxy_set_header X-Real-IP $remote_addr;
    	proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    	proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Example — Multiple Applications:
```
server {
    listen 80;
    server_name example.com;

    location / {

        proxy_pass http://frontend:3000;
    }

    location /api {

        proxy_pass http://api:5000;
    }

    location /admin {

        proxy_pass http://django:8000;
    }
}
```

Load-Balance:
```
upstream backend {

    server app1:8080;
    server app2:8080;
    server app3:8080;
}

server {

    location / {

        proxy_pass http://backend;
    }
}
```

## compare storage protocols

**When should you use each?**
| Situation                     | Best Choice                    | Why                                                     |
| ----------------------------- | ------------------------------ | ------------------------------------------------------- |
| Linux-to-Linux shared folder  | NFS                            | Native, fast, simple                                    |
| Windows file server           | SMB (Samba)                    | Windows standard                                        |
| Mixed Windows + Linux office  | SMB                            | Best compatibility                                      |
| Upload files securely         | SFTP                           | Uses SSH encryption                                     |
| Copy configuration files      | SCP                            | Simple one-time transfers                               |
| Daily backups                 | rsync                          | Efficient incremental synchronization                   |
| VMware/Proxmox shared storage | iSCSI or NFS                   | Both are widely supported                               |
| Enterprise SAN                | Fibre Channel                  | Highest performance                                     |
| Kubernetes persistent storage | NFS, CephFS                    | Supports multiple pods                                  |
| Distributed cloud storage     | CephFS                         | Scalable and fault tolerant                             |
| Database storage              | Local disk, iSCSI, FC, NVMe-oF | Block storage offers better performance and consistency |
| User home directories         | NFS                            | Common in Linux environments                            |
| Shared documents              | SMB                            | Easy access from Windows desktops                       |

**File Storage vs Block Storage**
| Feature             | File Storage                  | Block Storage                                    |
| ------------------- | ----------------------------- | ------------------------------------------------ |
| Examples            | SMB, NFS, CephFS              | iSCSI, Fibre Channel, NVMe-oF                    |
| Users see           | Files and folders             | Raw disk                                         |
| Requires formatting | No                            | Yes (ext4, XFS, NTFS, etc.)                      |
| Multiple clients    | Yes                           | Usually no (unless using a clustered filesystem) |
| Best for            | Documents, source code, media | Databases, virtual machines, boot disks          |

* The Five Built-in Chains
	- **PREROUTING:** Processes packets as soon as they arrive, before any routing decision
	- **INPUT:** Handles packets destined for the local system
	- **FORWARD:** Handles packets being routed through the system to another destination
	- **OUTPUT:** Handles packets generated by the local system
	- **POSTROUTING:** Processes packets just before they leave the system

### NAT config

**Scenario 1 — Home/Office Internet Sharing (MASQUERADE)**

```
                 Internet
                     │
              Public IP
             198.51.100.20
                     │
                 eth0
             Linux Router
                 eth1
          192.168.1.1/24
                     │
      ┌──────────────┴──────────────┐
      │                             │
192.168.1.100                 192.168.1.101
```
Configure:
```bash
# NAT
iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE

# Allow forwarding
iptables -A FORWARD -i eth1 -o eth0 -j ACCEPT

iptables -A FORWARD -m conntrack --ctstate ESTABLISHED,RELATED -i eth0 -o eth1 -j ACCEPT
```

**Scenario 2 — Company with Static Public IP (SNAT)**
Because the public IP never changes, we dont need MASQUERADE.
SNAT performs slightly better since the kernel doesn't have to look up the interface IP for each new connection.

```
Internet
     │
203.0.113.10
     │
 Linux Firewall
     │
10.10.0.0/16
```

configure:
```bash
iptables -t nat -A POSTROUTING -o eth0 -j SNAT --to-source 203.0.113.10
```

**Scenario 3 — Publish an Internal Web Server (DNAT)**
Your web server is private.
- Web Server: 192.168.10.20

But customers should browse
- http://203.0.113.10

```bash
iptables -t nat \
-A PREROUTING \
-p tcp \
--dport 80 \
-j DNAT \
--to-destination 192.168.10.20:80

iptables -A FORWARD \
-p tcp \
-d 192.168.10.20 \
--dport 80 \
-j ACCEPT
```
PREROUTING changes the packet's destination address, but it does not permit the packet to pass through the firewall. The FORWARD chain decides whether the packet is allowed to traverse the Linux machine.
